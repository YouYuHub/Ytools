# 历史修改后的上下文一致性

## 范围

涵盖 Chat Completions、Messages、Responses 有状态和无状态模式的历史插入、
编辑重发、单轮删除、截断删除、覆盖式重新回答，以及媒体标签等历史内容替换。

## 本地摘要

- 未受影响的摘要块保留，轮次编号随插入、删除平移。
- 完全被删除的摘要块移除，同时清除顶层兼容字段，防止旧正文再次被规整回摘要。
- 混有被删/被改轮次的摘要块无法可靠按句拆分：移除其旧正文及结构化字段，
  保留覆盖范围和摘要输出预算，记录 `repair_required`。
- 下一次聊天（包括历史重发）或手动压缩前，仅将待重建范围内仍存在的轮次交给
  配置的压缩模型。超长来源使用既有完整分段压缩流程；未受影响块不重新生成。
- 成功后原子替换修复块，并清理这些范围内已被纳入摘要的原文补充索引。
  对应的未压缩尾部仍照常发送；不会因曾使用 Responses 而清空整份摘要。
- 若旧摘要只有一个覆盖全部历史的累计块，修改其中一轮可能需要重建整个块。
  这会增加一次压缩的时间和用量，但不会把全部历史原文直接回传给聊天模型。
- 旧格式没有来源范围的摘要，使用当前轮次数建立保守的覆盖范围；无法关联的
  旧问题索引清除，模型请求中的问题索引从保留轮次重新生成。

## 远端响应链

Responses 编辑、插入开始时按有效前缀建立临时链；正常收尾和停止收尾都会
再次使该链失效。下一次续聊从完整的有效本地历史建立新链，包含位置后面的
保留轮次。删除、截断、直接内容替换和摘要重建也会使旧链失效。
远端状态文件是依据，不依赖元数据镜像一定存在。直接修改内容的轮次还会
移除旧原生回放引用，防止恢复修改前的服务商输出。

## 失败和边界

- 删除/编辑本身不发起模型请求；待重建标记持久化，刷新、重启后可继续修复。
- 重建失败、返回空内容或来源被截断时中止聊天，不发送过时摘要，也不回退发送
  整段原文；用户重试后继续重建。压缩过程使用原有模型重试与用量记录机制。
- 重建期间不持历史文件锁；提交时校验摘要及轮次快照，历史发生变化则拒绝覆盖。
- 历史压缩事件和备份仍用于审计；不把它们重新当作模型上下文。
- 后续已保留回答、引用快照不会自动改写或重新执行。删除一个来源轮次不等于
  删除其他保留消息中对它的复述，也不等于删除服务商已经存储的 response。
- 不自动迁移此前已清空或污染且无法确定来源的旧摘要；本次修改保护之后的操作。

## 三种 API 的协议行为与合理性

| 接口 | 协议行为 | 项目中的历史修改处理 | 判断 |
| --- | --- | --- | --- |
| Chat Completions | 每次提交 `messages`，应用自行管理历史 | 使用有效摘要、必要原文及当前问题重建请求 | 合理，便于任意历史编辑和跨模型切换 |
| Messages | 无状态多轮请求，应用每次提供需要的历史；工具交互使用原生内容块 | 使用同一套本地历史规则；原生工具交换仍由协议适配层维护 | 合理；消息 ID、思考签名或提示缓存不代表可省略本地历史 |
| Responses 无状态 | 本项目使用 `store=false`，提供本次所需 `input` | 与其他无状态接口一样从本地重建 | 合理，适合兼容服务及应用自行管理历史 |
| Responses 有状态 | 用 `previous_response_id` 接续远端响应链 | 历史改动后断开旧链，从有效本地历史建立新链 | 合理；本地历史改变后继续复用旧链会带回旧内容或漏掉保留轮次 |

协议依据：[OpenAI 会话状态](https://developers.openai.com/api/docs/guides/conversation-state)、
[Anthropic Messages 多轮请求](https://platform.claude.com/docs/en/build-with-claude/working-with-messages)。
无状态描述的是请求如何获得上下文，不表示服务商一定不留日志；提示缓存也不改变这一区别。

统一的产品语义是：插入位置之后的旧轮次保留；编辑只重跑指定轮次；单轮删除保留后续
轮次，截断删除则移除指定位置及之后的轮次。保留后续回答适合资料补充和局部修改，
但这些回答可能依赖修改前的上下文，系统不会自动重新生成它们。若用户希望所有后续回答
都基于新历史，应截断后重跑。这属于产品选择，不能由某一种 API 自动保证。

同一会话切换协议、Responses 模式或模型/账户时，按有效本地上下文续接；原生私有状态
不视为可跨模型传递。运行中的任务使用启动时的配置，切换在下一次任务生效。

部署需重启后端及其工作进程；建议等待正在执行的任务结束后重启。
