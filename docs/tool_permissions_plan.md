# 工具权限与用户执行确认方案

日期：2026-10-14。状态：已按后续授权落实首版。本文保留设计讨论，实际行为、接口和启动方式以 [工具权限使用与实现说明](tool_permissions.md) 为准；设计中的可选扩展不代表已经提供。

## 1. 推荐结论

在现有模型接口适配层之上、实际工具执行之前增加统一权限层，支持两种模式：

- **询问（`ask`）**：每次启动命令、每次调用 MCP 工具、每次内置工具访问当前工作目录及子目录之外的资源，都必须由用户明确批准本次调用。普通目录内的文件读取、搜索、写入和修改自动执行。
- **完全控制（`full_control`）**：维持当前工具使用行为，自动通过新增权限层；已有工具白名单、参数校验、资源上限和会话归属检查仍然保留。

用户确认通过独立的后端审批流程完成，不把“模型认为已得到同意”、系统提示词或聊天中的一句“允许”作为执行授权。每次确认只对应一次不可变的调用，不提供“后续全部允许”或“记住此工具”来隐式削弱询问模式。

主智能体、子智能体、三个模型 API 协议共用同一规则。子智能体不必获得 `ask_user` 工具，也能通过应用权限层等待用户批准。

补充需求（2026-10-14）：全局默认和会话覆盖均持久保存；后端关闭时尚未决定的审批及对应任务检查点也持久保存。重启后用户可重新批准/拒绝，再继续同一个逻辑任务，不能只恢复一张没有执行上下文的卡片。详细规则见第7.5节。

这属于**应用内工具执行确认**，并非操作系统沙箱。用户批准某条命令或某次 MCP 调用后，它可以具有当前系统用户的能力；工具中的任意代码、脚本、插件和网络行为无法靠一次弹窗完全约束。

## 2. 与当前实现的对应关系

| 当前入口 | 现状 | 方案中的接入位置 |
|---|---|---|
| `factory/chat_factory.py` 工具分发 | 内置文件工具直接执行，命令经 `to_thread` 执行，MCP 另走线程池 | 参数校验、调用计划生成之后，执行、读取、缓存和工具开始事件之前 |
| `factory/agent_runtime/sub_agent.py::_execute_tool_round` | 独立分发文件、媒体、文档、命令、MCP | 使用父任务传入的权限上下文与同一审批器 |
| `factory/agent_runtime/tool_executor.py::execute_tool_round` | 当前只负责 MCP 的解析/调用/并发结果 | 接收已授权调用的执行凭据，不能承担全部工具的唯一权限入口 |
| `factory/agent_runtime/builtin_tools.py` | 存在直接读盘、路径解析、媒体注册、下载、文档解析和命令执行等多种入口 | 为实际资源生成统一计划；关键读写入口验证执行凭据，搜索逐个检查候选路径 |
| `factory/session_worker.py` | 每会话独立进程，命令和事件经 Pipe 传递 | 新增审批申请、审批决定和执行状态消息；不能只在主进程创建一个 Future |
| `ask_user` | 生成问题后结束当前任务，答案作为下一条用户消息 | 可借鉴卡片样式；不复用它的执行语义 |
| `H5/js/app/chat.js` / `messages.js` | 已有流式事件、历史回放和子任务块 | 新增审批事件消费和卡片渲染，已有正文/工具事件格式保留 |
| `/file/get_local_file` 与媒体伪标签 | 模型回复的本地图片、PDF 等标签可触发浏览器自动取文件 | 询问模式下也检查目录边界，不能成为绕过工具确认的第二条读文件通道 |

尤其不能把 `try_execute_builtin_file_tool(...)` 当作无副作用的“工具类型探测”：它现在会直接执行工具。必须先按工具名选择处理器，生成计划和审批，再调用执行函数。

子任务现在部分 `tool_start` 在内置工具执行后才发出。接入权限时统一调整为“已批准且即将实际执行”再发送，审批等待使用新事件，避免前端把等待误显示为执行中。

## 3. 规则表

以下规则以询问模式为准。**一次调用**指一个确定的 `tool_call_id`、完整参数和执行目标，不是每次 `open()`、每个字节或每个 HTTP Range 请求。

| 操作 | 是否询问 | 具体规则 |
|---|---|---|
| `run_command` 启动命令 | 每次询问 | 前台/后台、只读/写入、工作目录内/外、命令看似安全与否都一样；不靠命令字符串猜测免询问 |
| `run_command(action=run)` 兼容形式 | 每次询问 | 与普通启动相同，不能漏过 action 分支 |
| MCP 工具 | 每次询问 | 包括声明为只读的工具、当前工作目录内的文件工具；MCP annotations 不赋予免询问权 |
| `read_file`、`write_file`、`edit_file` | 目录外询问 | 访问范围包含读取旧内容、生成 diff、创建父目录、临时文件写入及最终目标 |
| `search_files` | 搜索根目录在外则询问 | 本次批准包括在该搜索根及子目录按已展示参数搜索；不授予其他调用访问该目录的权利 |
| 目录内搜索遇到指向外部的链接 | 不自动访问 | 跳过并返回 `skipped_permission` 等计数；模型要读该外部目标时另发一次需要批准的调用 |
| `read_media` 本地来源 | 目录外询问 | 读取、文件头探测、转码、复制入库之前确认；同一调用的多个来源统一展示 |
| `read_document` 本地来源 | 目录外询问 | 原生文档读取、文字解析、表格解析、缓存恢复重读原文件均覆盖 |
| `read_media` HTTP(S) 来源 | 建议询问 | 视为外部资源访问，显示来源 URL；不能把 URL 当成目录内路径。此项是对用户给出的本地路径规则的补充 |
| 当前会话的已上传媒体/文档 | 不询问 | 通过合法会话资源 ID 读取用户已交给应用的副本，不依赖它在磁盘上恰好位于工作目录外 |
| 已批准的外部文件被复制为会话媒体副本 | 读取副本不重复询问 | 只允许读已登记的那份副本；重新读取外部原文件仍需新确认，不可将库路径当作任意文件白名单 |
| `todo_write`、`ask_user` | 不询问 | 属于应用内计划/问答，不具有任意路径执行能力 |
| `sub_agent` 派发 | 派发本身不询问 | 子任务每次实际执行命令/MCP/目录外访问时按同一规则询问；不能靠委派提升权限 |
| `poll_command`、`stop_command`，以及对应 action | 不另询问 | 只针对本会话已有的、合法创建的后台任务读取日志或终止进程；禁止夹带 command、shell、work_dir 等新执行参数 |
| 用户点击终端停止、文件撤回、上传等应用操作 | 不作为模型调用弹出工具确认 | 这些由用户直接触发，保留原有会话检查和操作确认；不能让模型伪造用户操作来源 |
| 历史存储、日志、审批审计、diff 侧车、转码临时文件 | 不因位于目录外重复询问 | 属于后端根据已批准操作生成的固定内部存储；位置必须由应用决定，不能由模型指定 |
| 模型推理请求、标题生成、上下文压缩 API | 不属于本功能的工具确认 | 继续遵循现有模型设置与网络异常处理 |

多来源调用采用明确的整次决定：例如一次 `read_media` 包含两个目录内文件和两个目录外文件，卡片列出四个来源、标明越界项；批准后执行本次列表，拒绝则整次不执行。不悄悄缩减参数后执行“另一种调用”。

批准 `run_command` 表示批准完整命令及它调用的脚本/子进程，不能靠显示的 cwd 保证命令只访问这个目录，也不在命令内部每一次文件 I/O 时再弹窗。若要求已批准命令也无法自行访问外部文件，需增加 OS 级隔离；这与本方案的“每次启动命令前确认”是不同能力。

### 3.1 额外的控制面保护

普通目录内访问默认不询问，但应用自身的权限配置、审批令牌和决定通道不能因此自动暴露给模型。若工作目录恰好就是 Ytools 项目目录，这些文件可能也落在“目录内”。

询问模式下对权限控制资源的模型读写至少需要单独确认；权限模式只能由鉴权的用户配置接口改变，普通文件改写不能在运行中直接授予执行权限。内部凭据和执行上下文字段不能从模型 JSON 参数中导入。该补充是为了防止模型通过改权限配置自行获得完全控制，普通业务文件不受影响。

## 4. 目录边界与资源解析

### 4.1 使用真正生效的工作目录

现有 worker 会解析会话目录并 `os.chdir`，失效时还可能回退。权限根必须取**该任务最终实际生效的目录**，而非前端展示文本、主进程 cwd 或模型提交的 `work_dir`。

生成任务开始时创建不可变上下文：

```json
{
  "session_id": "yt-example",
  "generation_id": "gen-random-id",
  "worker_instance_id": "worker-random-id",
  "permission_mode": "ask",
  "workspace_root": "C:/example/workspace",
  "policy_revision": 7
}
```

相对路径明确基于该根解析。命令中的 `cd`、子进程工作目录或用户在任务中更改目录，不会自动扩大该任务权限根。

根目录无法确定、切换失败且没有明确有效回退时，询问模式停止自动文件访问并提示用户选择有效目录。不要无声把应用目录或磁盘根当成授权根。

### 4.2 判定规则

1. 对路径按执行器实际语义处理绝对/相对路径、`~` 和受支持的环境变量。若当前工具不支持环境变量展开，权限层也不能擅自展开出不同目标。
2. 使用规范化路径及父子目录关系判断，不能用 `startswith`：`C:/work-other` 不在 `C:/work` 内。
3. 处理 `..`、Windows 大小写、驱动器、UNC、符号链接和目录联接。目录内链接指向目录外时按外部路径处理。
4. 新建文件同样检查已存在的父目录和真实目标；不存在的尾部不能绕过父目录链接检查。
5. 文件路径规划只做归一化和必要的边界元信息检查；审批前不读取正文、枚举外部目录、生成 diff、探测媒体或运行解析器。
6. 搜索不是仅检查一次根目录。遍历时也检查子目录及文件的真实目标；目录联接可能与普通符号链接行为不同，不只依赖 `followlinks=False`。
7. 将已解析的资源计划交给执行器使用，避免权限层和执行层各解析一次得出不同文件；会话文档名称查询、`media://`、本地文件回退必须共用资源解析结果。

对于完整 URL、会话资源和文件路径，用明确的资源类型分支，不能对所有字符串统一套 `Path`。`read_document` 命中了会话上传副本还是准备回退读本地文件，要在批准前确定。

### 4.3 执行前再次复核

确认期间目录、链接或文件可能变化。执行前复核根目录与目标的真实路径/身份、工具参数摘要及 MCP 服务配置版本；改变执行目标就让旧授权失效，重新规划，而不是把批准迁移到新目标。

这能降低普通的路径替换风险，但 `resolve()` 后再 `open()` 仍有竞争窗口，硬链接也不是符号链接。若要求对恶意并发替换、硬链接和任意命令提供严格隔离，需要基于文件句柄的限制和 OS 沙箱；不能声称仅靠规范化路径已经实现这一能力。

## 5. 执行管线与模块设计

建议增加三个小模块，保持模型协议适配层不感知权限弹窗：

- `permission_policy.py`：纯规则，输入权限上下文、不可变调用计划，输出 `allow / require_approval / deny` 和理由。
- `tool_execution_plan.py`：根据工具类型生成实际资源、标准化参数、执行目标和审阅信息；不执行模型所请求的动作。
- `approval_broker.py`：审批生命周期、主进程注册表、worker Future、取消和 IPC 协调。

```mermaid
flowchart LR
    A[模型产生工具调用] --> B[白名单与参数校验]
    B --> C[生成不可变执行计划]
    C --> D[权限规则]
    D -->|目录内或完全控制| G[执行前复核]
    D -->|需要询问| E[登记请求并推送确认卡片]
    E -->|用户批准本次| G
    E -->|拒绝或过期| H[返回对应工具结果]
    G --> I[发送 tool_start 并执行]
    I --> H
    H --> J[模型继续或任务结束]
```

伪代码：

```python
plan = build_execution_plan(validated_call, permission_context)
decision = evaluate_policy(plan, permission_context)
permit = await approval_broker.authorize(plan, decision, cancellation)
if not permit.allowed:
    return permission_tool_result(plan.tool_call_id, permit.reason)
revalidate_target(plan, permit)
await emit_tool_start(plan)
return await execute_approved_plan(plan, permit)
```

实际执行函数必须需要服务端产生的执行凭据，或由无法绕过的受控执行适配器调用。凭据包含调用摘要和任务身份，不是模型参数中的 `approved=true`。完全控制也通过这一入口自动生成凭据，避免两条执行路径以后漂移。

不要仅靠 `contextvars` 向 MCP 线程池传权限：当前代码还会创建 `ThreadPoolExecutor` 和独立事件循环。父/子智能体、工作线程、MCP 调用均显式传递必要的授权上下文。

### 5.1 并发

一个模型轮可能同时请求多个工具。先规划全部调用并登记需确认的项，然后每项等待自己的决定；目录内无需询问的调用和已经批准的调用可以先运行。

等待用户期间不占 MCP 执行线程池和命令执行并发槽。保留现有主/子任务总体并发上限，不为审批无限生成任务。工具结果仍按调用 ID/原始顺序回收，模型轮在所有调用获得结果后才能继续。

弹窗可以有待处理队列和每项独立按钮，首版不提供一键批准所有待确认项。一次调用的多个资源在同一卡片上批准，多个 `tool_call_id` 仍分别批准。

## 6. 审批生命周期、IPC 与接口

### 6.1 身份与状态

每个审批至少绑定：`approval_id`、会话 ID、generation ID、worker 实例 ID、主/子 agent ID、工具调用 ID、工具来源/原始名称、参数摘要、目标资源摘要、策略版本、创建与过期时间。

`approval_id` 使用不可预测的随机值。调用摘要覆盖完整参数、shell、cwd、资源范围、MCP 配置身份等；不能仅按工具名或命令前缀复用批准。

状态建议：

```text
pending -> approved -> executing -> completed / failed / outcome_unknown
pending -> denied / expired / cancelled
pending -> suspended_waiting_approval -> 新审批 pending
approved -> cancelled_before_execution / invalidated
```

批准决定采用原子状态变更，只能对仍属于活动任务的 pending 项生效。双击、多个页面同时确认和网络重试不得重复执行。已经批准的请求再次提交同一决定返回当前状态；相反决定或过期/失效请求返回409。不存在的请求返回404。

UI 不凭 POST 成功就显示“执行完成”。主进程接收决定后，worker 需要验证、消费执行凭据并回报执行状态。停止任务与确认同时到达时，停止/失效状态阻止尚未开始的执行；已经开始的操作按已有取消能力尽力停止，不能宣称撤销了已经发生的副作用。

### 6.2 跨进程

1. worker 为执行计划创建等待 Future，向主进程发送 `approval_requested`。
2. 主进程审批器先登记 pending，再通过现有会话 SSE 推送新事件。
3. 用户点击后，主进程验证身份、所属任务和请求状态，经命令 Pipe 发送 `approval_decision`。
4. worker 命令循环处理决定，核对对应计划，唤醒那个 Future；运行中的生成任务不能阻塞命令循环。
5. worker 回报 `approval_consumed`、执行开始/结束，主进程更新状态并发 SSE。
6. 用户 stop、子任务停止取消其审批；worker 崩溃和服务重启使旧进程执行凭据失效，保留持久任务供恢复，不把未决定的申请当成已拒绝。

inline 模式使用同一接口的本地实现，不能只支持 worker 模式。主进程维护展示/路由状态，worker 持有实际执行等待；避免以文件轮询充当决定投递机制。

### 6.3 建议 REST 接口

| 接口 | 用途 |
|---|---|
| `GET /chat_config/permissions?session_id=...` | 全局默认、会话覆盖、当前任务生效模式和根目录 |
| `POST /chat_config/permissions` | 由用户修改全局默认或会话覆盖，支持恢复跟随全局 |
| `GET /tool_approvals/pending?session_id=...` | 打开/切换会话、刷新/重连时取活动及可恢复审批快照，注明任务是否因重启而挂起 |
| `POST /tool_approvals/{approval_id}/decision` | 批准或拒绝本次；对恢复卡片同时启动任务续跑，必须鉴权并绑定当前执行代次 |

请求示例，仅提供决定和关联校验字段；执行参数始终来自服务端原计划：

```json
{
  "session_id": "yt-example",
  "generation_id": "gen-random-id",
  "decision": "approve"
}
```

响应可为202已接受并等待 worker 消费；前端通过状态事件或一次性刷新确认最终状态。决定提交超时先查当前审批状态，再决定是否重发，不能另创建相同执行。

### 6.4 SSE

示例，新增独立事件，不改既有 `content`、`tool_calls`、`tool_start`、`tool_return` 格式：

```json
{
  "event": "tool_approval",
  "phase": "requested",
  "approval": {
    "id": "approval-random-id",
    "session_id": "yt-example",
    "generation_id": "gen-random-id",
    "agent_id": "main",
    "tool_call_id": "call-example",
    "tool_name": "run_command",
    "reason": "command_execution",
    "command": "python -m pytest test/test_example.py -q",
    "shell": "powershell",
    "cwd": "C:/example/workspace",
    "background": false,
    "state": "pending"
  }
}
```

其他 phase 表达决定和执行状态，按 approval ID 合并。SSE 可以重复回放，前端必须去重；**是否还能确认以活动审批接口为准，历史卡片不能执行**。

不新增持续轮询：待确认由 SSE 唤醒，恢复页面时取一次快照；确认提交状态不明时才针对当前请求查一次状态。切会话不取消后台任务的审批，只切换显示和对应角标。

## 7. 配置、快照与历史存储

### 7.1 模式真源

采用“全局默认 + 会话覆盖”，与现有工作目录/模型选择习惯一致；权限真源统一放在本机 `history_files/state/permission_runtime.sqlite3` 的 `policies` 表，不拆分到 `.env` 或会话 JSONL。新会话、旧会话缺配置和非法值均默认 `ask`。

会话覆盖明确支持三种配置值：`null` 表示跟随全局，`ask` 表示该会话固定询问，`full_control` 表示该会话固定完全控制。全局默认更新会影响未覆盖会话的下一次任务，显式覆盖的会话不受影响；关闭后端、刷新前端和重启服务都不清除这些设置。

用户可显式设置全局完全控制，后续未覆盖的会话跟随它。首次升级给出一次模式选择入口；不自动根据“过去一直能执行”推断用户授予了完全控制。

`_meta` 如需展示可保存非权威镜像或版本，不能用导入历史里的 `permission_mode=full_control` 作为授权。按 2026-10-15 的后续需求，分享改为携带仅所选会话配置的 SQLite 快照；导入弹窗展示配置，用户确认导入后按最终会话 ID 合并，支持 `ask`、`full_control` 与跟随接收端全局。接收端全局和其他会话不变，不能直接覆盖整个数据库；凭据、任务、历史批准和活动审批不迁移。旧包与单 JSONL 无快照时保持本机配置，不能从聊天文本授予权限。

权限配置接口与执行审批决定需要相同的用户控制面鉴权。模型请求体中的模式、根目录、`_session_id`、`_agent_id`、批准标记等不能覆盖服务端权限上下文。

### 7.2 任务内稳定性

首版推荐任务开始时冻结模式、权限根和策略版本；子智能体继承这一份快照。用户在执行中改设置，**下一个任务生效**，界面同时显示当前任务模式，避免误解。

因此从询问改成完全控制不会自动放行当前 pending 项。可以批准本次，或停止当前任务后用新模式重新开始。临时 `cd` 也不能改变权限根。

这样能避免半轮工具中一部分按旧模式、一部分按新模式执行。如果未来要热切换，必须通过控制 IPC 原子地切换并使旧请求失效，不能通过每次读 `_meta` 拼凑实现。

### 7.3 活动状态与审计

- 主进程内存注册表与 worker Future 是运行时投影，不是持久真源。任务、待决定审批、执行状态和确定结果持久保存；重启后重新建立投影与 Future，但不恢复旧执行令牌。任务恢复见第7.5节。
- `chat_round.events` 记录申请、用户决定、执行状态等**审计事件**，包含调用关联和必要参数摘要，不记录确认令牌。
- 当前 `chat_round_store` 有事件校验白名单，需要新增权限事件规则、解析和历史渲染；不能随意塞一个无 role 的事件后以为它会被保存。
- 三种模型上下文转换仅接收实际工具调用及结果。审批过程本身不转换成 user 消息，不进入 Responses 的远端状态链，也不靠重新提交用户问题恢复。
- 用户拒绝/过期时回传普通工具结果并保留原 `tool_call_id`。Messages 转成对应 `tool_result`，Responses 转成对应 `function_call_output`，Chat Completions 继续使用 tool 消息。

工具结果示例：

```json
{
  "success": false,
  "code": "PERMISSION_DENIED",
  "executed": false,
  "message": "用户拒绝了本次执行，请使用已允许的资源或直接说明限制"
}
```

这一结果表示明确未执行，不算网络失败，不触发网络自动重试。等待、过期、任务取消和执行结果未知也要分别表达，避免全部混成工具执行异常。

### 7.4 重试与断线

前端断线不等于拒绝，也不能等于同意。worker 保持等待，用户刷新后通过 pending 快照恢复。建议独立的审批有效期为15分钟，到期明确不执行。

模型网络重试只重试推理请求，不能隐式重跑已执行工具。Responses 恢复读取已缓存的工具结果时没有新的实际执行，不需要重新确认。若确定要再次实际执行，必须生成新的执行实例并重新确认；结果未知则沿用已有恢复机制提示核对，不自动重试副作用。

Responses 尤其要区分“尚未获准，所以确定没有执行”与“已经开始执行，但结果未知”。停止任务时，前者可在本地工具结果 journal 登记 `cancelled / executed=false`，后续继续原链时补齐对应 `function_call_output`；不能因它未获批准就落入已有“上次工具执行结果未知”的恢复分支。拒绝和审批过期结果同样登记为确定的工具结果，审批令牌与决定通道不进入远端 input。

外部 URL 的批准绑定原始来源和允许的重定向规则。首版建议不自动跟随到不同 origin；需要新来源时返回明确结果并重新申请，不能让一次 URL 确认变成任意网络地址通行权。

没有前端的 API 客户端也遵守询问模式：调用方可以通过鉴权的审批 API 确认，或由用户事先在配置中选择完全控制。缺少客户端不是自动放行理由。

### 7.5 服务关闭后的持久恢复（补充）

**目标：用户未选择允许/拒绝就关闭后端，重启并打开该会话后，仍能选择允许/拒绝并继续原任务。** 这项能力应纳入首版，而非仅保存用于诊断的审批记录。

#### 持久真源

使用本机 `history_files/state/permission_runtime.sqlite3` 保存任务与审批，与权限策略统一存储；任务和审批不随会话导出/导入，仅会话权限配置使用独立过滤快照随包迁移。旧版 `sidecars/permission_runtime.sqlite3` 在停止旧后端并启动新版本后自动迁移并保留备份。使用事务和可靠提交；任何恢复所必需的检查点未保存成功，就不发布可批准卡片，也不开始工具执行。

至少保存以下状态：

| 数据 | 内容 |
|---|---|
| 逻辑任务 | 稳定 `task_id`、会话/轮次、用户原问题与附件引用、运行/挂起/完成状态、版本、当前执行阶段 |
| 可续跑上下文 | 已完成模型输出、完整工具调用批次、消息序列及其稳定 ID、必要的工具/模型配置身份和当前任务权限/工作目录快照 |
| 审批申请 | 不可变调用计划、标准化参数和目标摘要、原 `tool_call_id`、所属主/子 agent、待决定/已决定状态及审计时间 |
| 执行账本 | 同一批次每项的确定未执行、执行意图、执行中、确定完成/失败、结果未知；已完成工具结果及结果引用 |
| 子任务 | 每个 agent 的消息上下文、模型轮次、剩余活动预算、工具批次和已完成兄弟任务结果；不能只保存父级最终回复 |
| 原生协议状态 | Responses 的本地 journal/远端 head 引用与待回传结果，Messages 所需的原生内容和思考签名等；避免恢复后工具闭环或签名丢失 |

可重建的媒体字节、文档内容与大型原生响应优先使用已落盘资源引用，检查引用完整性；不要在每次 pending 更新时把全部 base64 重复写入审批表。认证 token、Future、线程/进程对象不序列化。

现有 `.pending` 只会把死进程的未收尾轮次恢复为 `interrupted` 历史，它不是完整的执行检查点。需要让 `ChatMemoryManager` 的恢复流程先识别这类可续跑任务，避免先将同一轮终结、清掉检查点，稍后又重复追加用户问题或工具调用。以 `task_id`、轮次及结果身份去重，收尾只提交一次。

#### 写入顺序与不重复执行

1. 保存整个待执行工具批次、续跑上下文和审批请求，事务提交后再发 SSE 卡片。
2. 用户决定持久提交后，才允许 worker 消费本次批准。
3. 调用工具前先持久标记执行意图/`executing`，提交成功后才启动实际操作。
4. 工具结果持久保存后再向模型继续发送；同批已完成的结果恢复时直接复用。

这并不能为任意外部命令提供“严格 exactly once”。若进程在第3步提交后、实际启动前崩溃，或在执行完成后、结果保存前崩溃，恢复端都可能无法判断是否执行过，应标为结果未知并要求核对，而不是猜测未执行后自动重跑。

#### 重启后分类恢复

| 关闭前状态 | 重启后的处理 |
|---|---|
| 正在等待用户决定，账本没有执行意图 | 确定未执行：保存为挂起待确认，前端重新选择后继续 |
| 已批准但尚未记录执行意图 | 不继承旧放行凭据：重新确认后才能执行 |
| 已有确定工具结果 | 复用结果，不重复调用、不为读取结果重复询问 |
| 执行意图/执行中，没有确定结果 | 标为结果未知，展示核验/重新规划入口；不能仅点一次普通“允许”就重跑 |
| 用户明确停止/取消，或任务已经完成 | 不自动恢复；保留只读历史审计 |

服务关闭与用户点击“停止任务”区分：正常服务关闭尽力写挂起检查点，之后取消进程内等待并释放资源，不把逻辑任务写成“用户取消”。强制结束进程也靠第1步已经提交的状态识别待确认任务；未被提交的内容不承诺能恢复。

启动时先核对旧 worker 的身份、进程存活与执行归属，再接管任务。不能假定主服务关闭后全部 worker/后台命令都已经退出，同时启动第二个执行者。执行实例采用新启动代次与所有权校验，旧实例不能使用新批准；未能证明旧执行者已停止的执行项按结果未知处理。

#### 用户恢复流程

1. 服务启动扫描持久存储，把可恢复任务列为 `suspended_waiting_approval`，暂不执行工具，也不重新向模型发送原问题。
2. 前端打开会话或重连时调用 pending 接口，显示“服务重启，任务等待重新确认”。其他会话可显示待恢复数量。
3. 展示原调用的完整命令/路径/MCP 参数；重新验证原工作目录、资源引用、服务配置和协议状态。
4. 用户点击“批准并继续”或“拒绝并继续”。决定接口以幂等恢复操作建立新 worker/Future，把该决定绑定到重新发布的请求，然后进入原批次的执行/拒绝结果流程。
5. 当前工具批次的结果齐全后，模型从这个检查点继续；不再重复生成先前工具调用。并行子任务分别恢复，各项仍分别确认。

逻辑 `task_id` 保持不变，执行代次、worker 身份、approval ID 和令牌重新生成，关联到原申请作审计。旧页面提交的旧 ID/旧代次返回409；新页面的重复提交返回当前恢复状态，不再次创建 worker。

若旧请求已经过了15分钟有效期，过期的是那份放行申请，而非将持久任务立即删除。重启恢复重新复核后发布新请求和新期限，用户必须重新决定；没有默认同意。

恢复原任务仍使用原权限根和原计划，不能把相对路径静默套到重启后的新 cwd。原目录失效、配置变化影响执行目标或检查点版本不兼容时，展示阻碍，让用户修改后重新规划，不把旧批准迁移到新参数。原任务曾在询问模式等待，即使全局现在改成完全控制，也不自动跳过这次重新确认。

Responses 的远端状态若在停机期间失效，按已有重新同步方案用本地上下文重建远端链，保持本地逻辑任务和未执行的工具计划。不得为重建链重跑已完成工具；无法可靠对应原生工具调用时暂停恢复，说明需要重新规划。原生协议状态完整性检查属于恢复前置条件。

## 8. 等待、取消和后台任务

用户阅读卡片的时间不应消耗命令/MCP/模型网络的执行超时；这些超时在实际操作开始后计时。不能在已经启动命令或 MCP 请求后才等待用户。

**子任务还需要单独改整体超时。** 目前有循环内 elapsed 检查，以及外层 `asyncio.wait_for(runner.run(), timeout=...)`，两者都会把确认等待算进去。建议改成活动时间预算 + 独立审批过期时间；活动计时暂停用户审批等待，恢复后继续计算，同时保留停止信号与异常兜底。多个审批重叠时扣除等待区间的并集，不把时间重复扣减。

等待中的 worker 保持任务活动，不按空闲 worker 回收；用户停止主任务时取消其全部 pending 和尚未执行的批准项，停止单个子任务时只取消该 agent 的请求。关闭后端服务则走第7.5节的挂起/恢复流程，不等同于用户取消。

一个被批准的后台命令可以在启动后继续运行，后续轮询输出不需不断重新批准；它是同一次启动执行。改命令、重启任务或执行新的进程仍要新确认。切换权限或停止聊天，不自动承诺已经启动的后台任务被终止，终端面板继续提供明确的停止入口。

## 9. 前端交互

### 9.1 模式入口

在当前工作目录附近增加权限按钮，显示“询问”或“完全控制”。按钮打开小面板，提供两种模式、全局默认/当前会话作用范围、恢复跟随全局。聊天设置中可放同一配置入口。

完整说明用一句话即可：

- 询问：“执行命令、调用 MCP 或访问工作目录外资源前，由你确认。”
- 完全控制：“模型可以直接使用已启用的工具。”

运行中的任务如使用旧快照，显示“当前任务：询问；新设置从下次任务生效”。权限配置与具体执行批准是两个不同操作。

### 9.2 确认卡片

工具块先显示“等待你的确认”，再弹出模态框，列表中保留卡片。推荐显示：

- 会话名、主智能体/子智能体身份和任务摘要。
- 工具名、来源和确定的审批原因。
- 命令：完整命令、shell、真实 cwd、前台/后台、执行超时。
- 文件：完整真实路径、读/写/修改/搜索动作、目录内/外标记；搜索展示根、范围、匹配规则和上限。
- MCP：服务器身份、原始工具名、完整参数。系统注入的连接密钥不放进事件或模型审阅文本。
- 来源参数和模型解释均当作普通文本显示，不执行 HTML，不允许模型说明覆盖后端判定。

按钮仅“批准本次”“拒绝”。关闭模态框、Esc、切会话表示稍后处理，保持 pending，不暗中批准或拒绝。聊天输入框显示等待状态，停止按钮仍可用。

多个请求按到达顺序排队，每项有独立 ID。当前会话 pending 数量显示在权限按钮上，其他会话显示角标，不让后台子任务的弹窗不断抢焦点。

## 10. 容易遗漏的旁路

### 10.1 自动加载的本地媒体

模型可以输出本地图片/PDF 标签，前端会调用 `/file/get_local_file`。因此询问模式下不能仅管 `read_media`：渲染器应先对外部来源生成待确认资源卡片，**批准前不设置会触发读取的 src**。

批准后取得短期、绑定会话和确定资源的读取票据，后端文件接口验证票据与真实路径。音频/视频的多个 Range 请求属于该次展示，不需要每个分片再次弹窗。页面刷新不从历史 HTML 中恢复长期通行权；过期票据需重新授权。

普通会话上传媒体继续使用会话资源接口。模型输出 HTTP 媒体标签也应沿用外部来源规则，防止回复直接触发外部资源请求；用户主动打开普通外链是另一种操作。

### 10.2 确认接口本身

当前后端没有统一身份认证，且 CORS 允许任意来源。新功能不能只凭 session ID、approval ID 或 Origin 就接受“批准”。

至少给权限设置、审批读取/决定及受保护文件读取增加独立的用户 UI 会话鉴权；建议将 H5 托管为固定本地 origin，或配置明确的 UI origin 白名单，并结合防跨站请求机制。当前 `file://` 页面 Origin 常为 `null`，不能把允许 `null` 当成可信前端认证。

可采用每次启动产生的随机配对凭据，通过用户启动页面时的 URL fragment 或本地配对流程交给 UI，换取短期控制会话；凭据不在模型参数、SSE、导出文件或日志查询字符串中传播，不使用一个无保护接口向任意请求者发放审批令牌。

这解决普通外部网页/其他 API 客户端随意替用户批准的问题。已经批准的 shell/MCP 若拥有同一 OS 用户的任意访问能力，仍可能读取浏览器/应用数据或调用本机服务；要严格隔离这种攻击，需要 OS 隔离和独立的可信审批通道，不能把应用令牌描述成针对任意同用户进程的安全边界。

### 10.3 MCP 发现与启动

工具定义获取、协议握手和服务器启动并不等同于一次模型 `tools/call`，现有客户端可能在发现阶段启动配置的 stdio 服务器。执行确认不能保证一个不可信服务器“启动时什么都不做”。

MCP 服务新增/修改属于用户配置和信任建立；确认卡片使用已知定义与配置身份，不为准备审批而预执行工具。启动前后核对服务命令/参数版本，配置变动使旧授权失效。若进一步需要“每次启动服务器也询问”，应作为独立的服务器启动策略，不能悄悄混入每次工具确认而造成双重弹窗。

### 10.4 权限拒绝造成的空转

系统提示告知模型当前模式和范围，但只作行为引导。拒绝后同一任务内相同计划的重新申请直接返回已有拒绝，不反复弹窗；明显只重复请求被拒绝操作时，按次数上限停止或要求模型说明限制。不同参数的调用不自动继承旧批准。

## 12. 实施顺序与验收

建议按以下顺序开发，但在全部门禁覆盖前不要宣称询问模式已经生效：

1. 明确权限真源与 UI 控制面鉴权，落地上下文、执行计划、路径/资源规则和单元测试。
2. 实现审批 broker、持久任务检查点/执行账本、worker/inline 投递、状态查询、取消、过期及重启恢复。
3. 接入主/子智能体全部执行入口、关键读写 helper 和临时/缓存资源路径。
4. 实现模式按钮、审批卡片、SSE/快照恢复及历史审计。
5. 覆盖本地媒体自动展示旁路，完成协议、重试、超时和导入导出测试。
6. 在临时目录和可控测试工具中端到端验收，再默认启用询问。

最低验收清单：

- 询问模式内层目录普通文件读取/搜索/写入不弹窗，父目录、其他盘、UNC、路径前缀相似目录均正确询问。
- 符号链接、Windows 联接、新建文件的链接父目录、搜索中途越界、确认后目标改变不能自动穿过边界。
- 命令每次询问，后台命令也一样；poll/stop 不能夹带新命令或管理其他会话任务。
- MCP 每次询问，包括只读工具、名称有命名空间和同名不同服务器的情况；批准前不发实际调用。
- 文件头探测、解析、原生 PDF、转码、文件 diff 和旧缓存回退都不在未授权时读外部正文。
- `media://` 只允许对应会话资源；本地/网络来源自动展示不绕过审批。
- 并行主/子调用分别确认，等待不占执行线程；父停、子停和审批过期不会放行迟到决定。
- 双击、多页面、断线重连、提交超时、worker 崩溃、重启和历史回放均不能重复执行或复活授权。
- 全局默认和每会话 `null/ask/full_control` 覆盖重启后保留；全局改动只影响跟随全局的会话下一次任务。
- 等待决定时正常关闭/强制结束服务，重启后可重新批准/拒绝并续跑；不重复用户问题、模型工具调用或已完成兄弟工具。
- 老页面决定不能批准新执行代次；到期申请可重新复核发布，服务停机不自动批准或丢失可恢复任务。
- 执行前意图已提交但结果未落盘的断点按未知处理，不自动重跑；用户主动停止与服务关闭的恢复语义区分。
- 审批等待不误耗工具执行超时，子任务整体超时也按活动预算处理。
- 拒绝有匹配 tool call ID 的结果，Chat Completions、Messages、Responses 三种协议均能继续闭环。
- Responses 恢复已完成工具结果不重跑；未知执行状态不自动重试。
- 导入权限仅来自用户确认加载的、经过校验的会话配置快照，允许恢复会话的完全控制选项；不携带全局策略、审批凭据、历史批准和任务检查点。模型参数和提示词不能修改权限上下文，本地其他会话不受影响。
- 完全控制模式维持现有工具行为，已有白名单、限制和会话归属检查不退化。

本方案的核心是“用户批准一次确定的执行，后端只执行这一份计划”。弹窗只是交互入口，真正的判定、身份验证、取消和一次消费都在后端完成。
