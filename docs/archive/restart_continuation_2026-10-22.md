# 后端强制退出后的会话接续

## 原因

服务退出后，当前轮的历史检查点和工具权限检查点会留在磁盘，原执行进程和 SSE 流则已结束。旧实现发现可恢复的权限任务时直接拒绝新消息；错误写入流缓冲后，聊天入口提前返回，没有将错误帧发送给浏览器，因此发送“继续”看起来没有响应。

另外存在几处会放大问题的状态不一致：

- 编辑重发将“挂起但未运行的任务”统一提示为“任务正在进行中”。
- 状态查询与附接之间任务可能已结束。空消息附接原先仍可能启动新的生成，而不是单纯读取已有流。
- worker 的准备阶段提前返回，可能没有发出 `task_done`，主进程一直保留运行态。
- 恢复检查点和创建流之间有异步等待，并发刷新可能看到尚未派发的半初始化流。

## 修改后的行为

### 重启后发送“继续”或其它新消息

1. 按会话串行处理恢复与派发；SSE 消费不占用该锁。
2. 检查旧任务的写者。只有已退出的进程留下的挂起任务才可被新消息接替；写者仍存活时明确报错，不擅自接管。
3. 为旧检查点取得带 epoch 的排他所有权，防止同时恢复/发送的请求重复接管。
4. 优先读取较新的轮次检查点，保留问题、引用、思考、工具和已有结果。工具账本中已完成但尚未进入历史的结果会补入历史；未执行的调用标记为未执行，执行结果未知的调用标记为未知并要求核对实际效果。
5. 将旧轮按 `interrupted` 收尾，保留原来的编辑替换/插入位置及历史摘要处理规则。历史保存成功后才关闭旧原生工具槽、清理旧权限检查点和结束旧任务预算记录。
6. 使用已保存历史和新消息启动真正的新一轮模型请求。前端会显示“已保存中断任务的轨迹并开始新一轮”的提示。

此流程不根据“继续”这个词匹配特殊命令，所有明确提交的新用户消息都适用。它从保存的上下文接续任务，不重放原任务中可能已经产生副作用的工具。新的工具调用仍受当前权限和预算配置约束。

### 保留原检查点精确恢复

在没有发送新消息前，仍可通过权限面板“恢复原任务”继续原检查点。原有的执行结果未知检查、配置指纹检查和审批失效处理仍有效。发送新消息后，旧任务已被接替，轨迹留在历史中，不再作为可恢复权限任务显示。

### 状态、重连和失败

- 无用户消息的请求只订阅实际存在的任务；任务结束或服务重启后没有活动流时，返回 `[DONE]`，不创建任务。
- 启动被拒绝、worker 派发失败、恢复写盘失败等错误会返回浏览器，并正常结束流，不再静默吞掉。
- worker 正常返回、提前返回及取消都必须发出结束信号；inline 模式同样兜底收尾。恢复派发尚未被 worker 接管就失败时，会释放主进程持有的恢复所有权，避免留下主进程 PID 永远存活的假运行态。
- 恢复写盘失败保留检查点并释放临时所有权，可重试；不会先删除恢复依据。
- 权限查询新增 `running`，表示实际生成态；编辑挂起任务显示“任务已中断 / 结束旧任务并重发”，实际运行任务仍显示“停止生成并重发”。

## 三种 API

- **Chat Completions**：从本地历史组装新一轮上下文，补齐工具账本能够确认的结果，未知操作明确标注。
- **Messages**：关闭旧原生工具槽，保存原始签名记录；新用户轮次使用现有事实投影机制，不把已关闭交换的旧签名思考当作当前工具轮继续。
- **Responses**：关闭旧原生工具槽并保留确认的结果；后续请求通过现有 Responses 上下文管理器组装输出与新消息，服务端链不可用时仍按原有规则重建本地上下文。

## 验证

新增 `test/test_restart_continuation.py`，覆盖真实杀死隔离测试进程后接续、已完成/未知/未执行工具、最新检查点、存活写者拒绝、恢复写盘失败、空重连、并发附接、启动失败、准备阶段退出、未接管的恢复派发及 Messages/Responses 后续请求构造。测试使用临时目录和模拟模型，不修改真实会话、不请求实际模型服务。

前端新增 `H5/test_h5/interrupted_task_edit.test.js`，验证运行态/挂起态提示与取消行为。

验证结果：新增后端恢复回归 16 项，连同相关审批、检查点、SSE 和三种协议回归共 **191 项通过**；前端全量 **621 项通过**。修改的 Python 模块编译检查和前端脚本语法检查通过。

后端代码更新后需重启服务，前端需刷新页面；静态脚本已更新内容版本。
