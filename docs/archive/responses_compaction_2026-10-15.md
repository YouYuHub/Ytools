# Responses 压缩生效与继续生成

排查会话：`yt-2026-10-14_08.36.53_548`。更新：2026-10-15，包含 11:00 空输入故障和 12:26 远端窗口故障。

## 已确认的原因

11:00 的“没有新的有效输入”来自本地检查。工具结果已经随 `compaction_trigger` 提交，本地摘要替换原轨迹后，普通生成检查不允许空输入。历史摘要、本轮工具摘要还重复请求了两次远端压缩。

初次修复确认了沿压缩 ID 可以继续生成及回忆事实，但没有验证上下文是否真正缩小。12:26 的记录补充证明：

- 平台返回了完整 compaction 密文。
- 沿压缩 ID 续聊仍报告 `input_tokens=462904`，当前配置窗口是 280000。
- 所以之后的本地远端预检拦截有依据；不能通过删除预检解决。

独立合成上下文的对照实测：

| 请求 | 输入 token |
| --- | ---: |
| 压缩前 | 22438 |
| 生成 trigger 压缩窗口 | 22471（处理压缩前窗口的用量） |
| 沿 trigger response.id 继续 | 22511 |
| 使用原生窗口建立新 `store: true` 响应 | 42 |
| 再通过新 ID 增量续聊 | 68 |

随机代号在两条路径中都能正确回忆。这表明当前 OpenCode 手动 trigger 路径返回了压缩产物，却没有在旧 ID 续链中裁剪祖先上下文；“生成成功”不等于“已启用”。这是兼容平台行为差异，加上项目此前对激活方式和验证范围的假定不完整。

## 当前实现

1. 工具结果和媒体仍在冻结边界中随压缩提交一次，获得完整原生输出。
2. 独立 compact 与 trigger 都先保留待启用窗口，状态为 `activation=pending_rebase`。
3. 下一次正常生成以完整原生窗口加未覆盖输入建立新 `store: true` 响应，不带旧 `previous_response_id`。任务进行中没有新用户问题时，原生窗口本身就是有效输入。
4. 新响应完整验证、持久提交后，才标记 `activation=active`，记录启用时的实际 input_tokens。后续继续正常 ID 增量调用。

这是有状态会话的一次初始化；没有增加每次回传全量历史的无状态模式。系统 instructions、工具定义和当前参数仍按原流程发送。密文保持原样，发送时只移除不属于输入 schema 的输出专属元数据。

## 旧会话与异常

- 旧 trigger 链在下一次请求时自动取“最近压缩项 + 其后提交的消息/工具调用”，加上未发送结果或账本中的已完成缓存结果，建立新链；不会只拿早先的密文而丢掉后来进展。
- 原会话只读预演得到 25 个输入条目，10 个最新已完成工具结果各保留一次，预检通过；没有修改该会话或执行历史工具。
- 压缩后续建链失败保留旧 head 和压缩窗口；收到响应 ID 后断流仍保持未知状态，先查询恢复。认证失败、截断响应及未确认工具不会被视作成功。
- trigger 的“响应提交 + 待启用状态”在同一锁内写入。进程中断、恢复查询返回压缩结果时，同样保留激活步骤。
- 用户选择 local/raw 重新同步时清除旧激活标记；模型、账户隔离继续生效。
- 连续两次本地摘要复用同一份原生窗口及用量；窗口之后的新结果和用户引导保留为待发送增量。

## 远端阈值与界面

Responses 的远端原生状态可能比本地摘要大。在任务的压缩检查点，额外用上一完整响应的 input/output usage 与待发送增量检查聊天模型窗口比例；达到阈值即触发原生压缩，即使本地不需要再次摘要。主任务与子智能体均覆盖，用量分别记入原压缩统计或子任务用量。

前端参数面板区分“压缩窗口待启用”和“已从官方压缩窗口建立新链”，后者显示启用时的实际输入用量。没有真实 usage 时不估算密文 token。累计消费用量不会因压缩下降，判断效果应比较单次响应的 input_tokens。

## 原会话继续
