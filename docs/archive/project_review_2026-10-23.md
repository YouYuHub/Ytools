## 范围与结论

本轮检查当前源码、工具定义、面向模型的说明、前端样式及历史/文件/终端的主要执行链；直接完成页面样式改进，后端改进以下列建议为准。没有运行自动化测试、压力测试或跨平台命令实验；性能项来自实现分析，不代表已测得的耗时。

项目已有严格参数校验、可取消执行、文件冲突检查、工具审批、会话归属校验和持久后台任务。下一步价值较大的工作是：**终端持续会话与增量输出、文件路径发现、明确文件版本记录状态、历史按需加载，以及配置语义统一。** 不需要为了模仿某个平台而增加大量重复工具和参数。

以下代码路径均相对于项目根目录。对比对象是本次 Codex 会话实际暴露的工具接口，不能据此推断所有 Codex 客户端或所有模型的能力相同。

## 文件四件套与本会话工具的差距

我在本会话中通常通过终端和 `rg` 读取、搜索文件，通过 `apply_patch` 修改文件；并没有一套与项目完全同名的原生“文件四件套”。对比应看完成任务的能力和调用成本。

| 能力 | 当前项目 | 本会话可用方式 | 建议 |
|---|---|---|---|
| 读取文本 | `read_file` 带行号、全文指纹、行分页和超长行续读，适合普通编辑 | 终端可组合各种读取/筛选命令，长输出也会截断 | 保留专用读取；优化大文件内部读取，避免每页重新处理全文 |
| 查内容 | `search_files` 默认普通文本，支持正则、上下文、预算和不完整标记 | `rg` 搜内容，按路径过滤并利用忽略规则 | 增加可续读结果和相对路径 glob；明确是否使用 `.gitignore` |
| 按名称找文件 | `file_pattern` 仅筛待搜索的文件名，不返回文件清单 | `rg --files` / 文件系统命令 | 高价值缺口：提供 `list_files` 或文件枚举模式，不要用内容搜索冒充路径搜索 |
| 新建/覆盖/追加 | `write_file` 必填模式，可带 `expected_hash`，返回结构化状态 | `apply_patch` 可创建文件；特殊写入仍用终端 | 当前模式清楚，应保留；追加不是整文件原子替换，需在工程说明中明确 |
| 修改局部 | `edit_file` 原文替换、单文件多处顺序编辑、冲突校验，失败不提交该批修改 | `apply_patch` 使用上下文补丁，可在一次调用中新增/更新/删除多个文件 | 增加可选 `apply_patch(patch)`，保留现有精确替换；不要使用模糊替换掩盖上下文不匹配 |
| 多文件变更 | 各文件需要独立调用和提交，可能部分成功 | 补丁可表达多文件修改；接口本身不保证跨文件事务 | 先全部解析/校验，再提交，逐文件报告结果；需要整体回滚时另做事务日志 |
| 变更保护和回退 | 指纹、同路径锁、版本检查、diff 和版本链是现有优点 | 本会话工具接口未承诺与项目相同的版本链 | 保留现有保护，并明确是否真的已记录可回退版本 |

### 读取与搜索的具体限制

`builtin_tools.py:1411` 的 `_read_text_snapshot` 对未命中缓存的请求仍先完整读取、解码和计算指纹。只有较小文本才进入缓存。因此 64 MiB 文件每次按 200 行翻页，输出虽然小，内部仍可能处理整份文件。建议按文件版本建立稀疏行索引，分段解码；全文指纹在同一版本内复用。编码、CRLF、文件变更和长行仍须保证正确，不能只按字节任意切 UTF-8。

`builtin_tools.py:1593` 的搜索用 `fnmatch(path.name, ...)` 筛文件名，没有相对路径 glob，也没有精确续读游标。达到展示上限后还可能继续扫描以计数。建议：

1. 默认只取有界结果，满足本页后尽早停止；完整计数按需启用。
2. 返回 `cursor/has_more/scan_complete`，区分“扫描中止”和“本页未展示完”。游标应绑定查询和文件版本，变更后明确失效。
3. 文件枚举只读目录元数据，不打开每个文件；支持相对路径筛选、隐藏文件和忽略规则的显式控制。

### 文件历史的限制应先说明白

工具支持处理到 64 MiB，但 `memory/file_history.py:46` 将版本链限制在任一端 **256 × 1024 字符**。`record_change` 超限返回 `recorded=false, skipped=file_too_large`；主流程 `factory/chat_factory.py:214` 调用后未回传这个结果，子任务也有同类消费点。修改成功不等于已经留下页面可回退的版本。

建议优先返回并展示 `history_recorded` 和原因，记录异常也要可见；随后再考虑压缩快照、差量存储和单会话配额。`write_file` 的追加当前是原地追加，并非整文件原子替换；外部编辑器不遵守工具锁时，版本检查到提交之间也不能视为操作系统级原子 CAS。

## 终端工具的差距与建议

| 项目 | 当前项目 | 本会话实际接口 |
|---|---|---|
| 普通执行 | 前台等待结束或总预算到期；默认 120 秒，范围 1–1800 秒 | `exec_command` 可等待一段时间后返回部分输出与活动 `session_id` |
| 等待与超时 | 一个 `timeout_seconds` 表示运行预算，后台不使用 | `yield_time_ms` 控制本次等多久；返回会话后进程可继续运行 |
| 后续输出 | `poll_command` 取最新日志尾部，可能重复，也可能漏掉两次采样间的内容 | `write_stdin` 可以继续取该会话的新输出 |
| 交互 | 标准输入为 `DEVNULL`，没有模型侧 PTY/交互输入工具 | 支持活动会话输入，按环境可申请 PTY |
| 独立服务 | `background=true` 创建独立持久任务，带注册表、归属、进程身份和日志 | 不能从本会话接口推断同等的重启持久化保证 |
| shell 状态 | 每次 `run_command` 是新 shell；跨调用不继承 `cd` | 每次新的 `exec_command` 也不能假定共享状态；只有同一个活动进程/会话内部可以保留状态 |

**120 秒默认值本身合理。主要缺口是“等多久返回”与“进程最多运行多久”没有分开。** 单纯把默认超时改大，会增加模型等待；改小则可能提前杀掉正常构建或分析任务。

推荐按顺序实现：

1. 增加 `yield_time_ms`：短暂等待后，未结束则返回活动会话 ID 和已产生输出。保留现有运行总预算与取消语义；活动会话随当前任务取消，显式后台任务继续独立管理。
2. `poll_command` 或统一续读接口增加 `cursor` 和有界 `wait_seconds`，返回 `next_cursor/has_more/status/exit_code`。游标应能识别日志轮转和多字节编码边界，避免遗漏和重复；兼容旧的尾部采样模式。
3. 确有交互需求时，再增加 `write_stdin` 和可选 PTY；Windows 需要设计 ConPTY、编码、EOF、信号和进程回收，与当前 WMI 隐藏后台启动链分别实现。
4. 给完整日志增加容量统计、保留策略和轮转。目前 `_prune_old_bg_files` 保护所有未关闭记录，即使命令已经结束；完整日志没有磁盘容量上限。清理应有预览，运行任务和用户保留记录应受保护。
5. 页面提供“最近已结束任务”，便于查看、下载和关闭记录；当前入口只在存在运行任务时出现，任务结束后清理入口难以发现。

## 其他工具与面向模型的文档

- **子智能体：** 当前支持同轮并发派发和前端流式展示，父模型只收到最终报告；任务必须自包含，子任务不能再次派发或提问。本会话另有消息、等待、继续和中断接口。只有长任务确实需要中途协调时，才值得增加任务句柄和定向补充要求；先保留简单派发的低调用成本。
- **媒体/文档：** 现有按模型能力决定原生输入、分页/分段回传和 `loaded/skipped` 结果是优点。本会话 `view_image` 主要解决本地图片查看，不能因此认定项目的文档/音视频工具更弱。后续重点放在大文档索引复用和一致的续读字段。
- **网页/浏览器：** 抓取/搜索与浏览器操作用途不同。项目已分别提供这些能力，应继续通过工具选择和少量任务路由说明让模型选对工具，不用把抓取工具扩展成浏览器模拟器。
- **说明书：** 当前 `docs/builtin_tools.md` 已足够简洁。模型每次主要需要可见工具 schema 和短规则，不必把审计报告、实现细节及全部故障历史加入系统提示词。新能力只补“何时用、必需字段、怎样继续、怎样结束”四件事。
- **参数一致性：** 保持 `path/work_dir`、行号从 1、字符/输出游标从 0，以及秒/毫秒的后缀明确。不要为了相似而批量改名；新增字段兼容旧协议，用别名迁移并在 schema 中只展示推荐写法。

面向模型的新终端说明可以压缩为：

> 运行命令用 run_command。未结束时用返回的 ID 和 cursor 续取输出；需要交互时用 write_stdin。独立服务显式 background=true。运行预算与本次等待时间分开。

以上是未来能力落地后的示例，目前不能提前加入真实工具说明，以免模型调用不存在的参数或工具。

OpenAI 的 [Shell 文档](https://developers.openai.com/api/docs/guides/tools-shell) 与 [Apply Patch 文档](https://developers.openai.com/api/docs/guides/tools-apply-patch) 可作接口设计参考。[Codex 提示指南](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide) 也建议适合模型的补丁和 shell 接口；文件修改的事务性和路径边界仍由执行端负责。项目兼容多个协议和供应商，建议先做通用函数工具形式的补丁适配，再按模型能力选择是否使用原生接口。

### 推荐实施顺序

1. 先修“行为是否可理解”：重试次数统一、版本记录状态、已结束终端记录入口。
2. 再补模型高频能力：文件枚举、终端短等待返回、按游标取输出、搜索续读。
3. 再扩展编辑能力：多文件上下文补丁、明确部分失败和回滚边界。
4. 最后根据实际体量优化：大文件索引、服务端历史分页、日志配额、可选交互 PTY。
