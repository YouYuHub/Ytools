# 模型提问续答后的实时显示

## 问题

用户从模型自动弹出的提问窗口提交回答后，后台任务继续执行，但当前页面没有显示后续思考、工具和正文，刷新才能看到。

排查确认续答链路存在以下缺陷：

1. 最新提问的回答也携带 `insert_round`，进入历史插入分支。这个分支原来没有 `round_started`；前端虽然给节点标了轮次，却没有设置活动流的 `round`，导致轮次身份不完整。
2. 发送和附接先创建节点、滚动，之后才登记活动流。滚动会同步切换历史窗口，此时窗口恢复可能拿不到本次流。后续管线一直持有原回复节点，即使它已脱离页面，也继续向这个节点写内容。
3. 创建 SSE 订阅时使用了重连回放起点。worker 如果在订阅前已经推进到该位置，新请求会跳过前面的轮次确认和模型信息。
4. SSE 读取器把 JSON 解析和页面回调放在同一个 `try/catch` 中，页面处理异常被作为无效 JSON 静默忽略，难以观察实际显示错误。

这些属于项目的续答、流订阅和页面显示逻辑，不依赖模型参数。

## 完成的修改

- 最新提问的回答使用普通追加；确有后续对话的历史提问仍保留确认、插入和更新回答的操作。
- 普通发送、原地重发和历史插入都在提问检查点保存后发送 `round_started`。显式编辑或插入在前端也提前登记已知轮次。
- 先登记活动流，再挂载节点和滚动。新用户气泡先在临时片段中构建，避免构建过程中提前触发置底。
- SSE 事件到来时，如果当前会话的活动回复容器已脱离尾部窗口，将原用户气泡和回复容器重新挂回；使用同一个容器和管线，不重复发起模型请求。
- 用户阅读较早历史、切换会话、旧流被接替或明确脱接时不强制挂回，不抢阅读位置。
- 创建者从第 0 帧消费；重连订阅继续使用原有回放起点、marker 和去重机制。
- 读取器只忽略无效 JSON，页面处理异常交给聊天层显示；结束、异常和 `[DONE]` 时释放读取器，同时处理未换行的最终数据行。

以上处理位于三种 API 共用的生成入口和前端管线，Chat Completions、Messages、Responses 的上下文组装方式保持原有规则。
