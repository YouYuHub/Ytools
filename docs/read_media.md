# 内置媒体读取工具 read_media

## 1. 用途与启用条件

`read_media` 让模型按需查看图片、音频、视频，接受会话附件引用、本地文件和网络直链。具体可用媒体取决于当前协议：项目的 Messages/Responses 适配目前只接受图片，音频/视频会明确拒绝，动图按静态首帧处理。文档使用 `read_document`，普通文本使用 `read_file`。

前端「配置工具」→「内置工具」中勾选 `read_media`，且执行任务的模型配置 `vision=true`，工具才对模型可见。子智能体按其实际使用的模型判断。`vision=true` 是项目中的启用门槛，并不能证明供应商支持音频、视频或多张图片；这些限制由 `mediaLimits` 和供应商实际行为决定。

## 2. 参数

| 参数 | 必填 | 含义 |
|---|---|---|
| `references` | 是 | 字符串数组，最多 5 个来源：`media://`、本地路径、HTTP(S) 媒体直链，可混用；重复来源按顺序去重 |
| `quality` | 否 | 图片质量 50–100，默认 85；主要用于大图降采样，不代表视频质量或音频质量 |
| `start_time` | 否 | 视频/动图开始秒数，支持小数，非负；省略从 0 开始 |
| `end_time` | 否 | 视频/动图结束秒数；省略按开始时间和单次读取上限计算；不能小于 `start_time` |

本地相对路径以当前会话工作目录为基准。本地文件不会自动复制到会话媒体库，因此后续重读需要原文件仍在。网络 URL 应直接指向媒体文件，普通网页使用 `fetch_url`；常规直链可由供应商拉取，需转换的格式可能由后端下载处理。

### 查看一张图片

```json
{"references": ["media://uploaded_image.png"]}
```

### 查看多个来源

```json
{
  "references": [
    "C:/example/images/photo.png",
    "https://example.com/example.jpg"
  ],
  "quality": 85
}
```

模型应遵守请求中的有效媒体配额：若仅允许一张图片，就分多轮分别读取。同一条模型回复只调用一次 `read_media`；同批多个来源放在一个 `references` 中，超过限制的来源会被跳过。

### 分段查看本地视频

```json
{
  "references": ["C:/Videos/demo.mp4"],
  "start_time": 0,
  "end_time": 30
}
```

读取下一段时以返回的 `video.read.end` 为起点，不直接假定请求中的结束时间已经全部读取。单次区间上限由全局 `VIDEO_MAX_READ_SECONDS` 控制，默认 60 秒，生效范围 5–3600 秒；超长区间会截断并返回实际区间。时间按帧边界吸附，实际区间可能与请求略有差异。

`start_time=end_time` 用于元数据探测，不发送视频画面，但仍受工具加载和已知媒体类型限制检查。网络 URL 指定时间区间会直接报错；需要切片时先下载到本地。静态图片和音频不使用这两个区间参数。质量必须是整数，时间必须是非负有限数字。

## 3. 返回与回传链路

工具结果包含状态与元信息，不包含 base64：

| 字段 | 含义 |
|---|---|
| `ok` | 至少一个来源成功读取时为 true；不能据此推断所有来源成功 |
| `message` | 本批读取状态摘要 |
| `loaded` | 成功来源元信息：引用、来源类别、媒体类型、质量、转换情况、视频区间等 |
| `skipped` | 未成功来源及原因，例如重复、文件不存在、超限、供应商配额限制 |
| `injected_references` | 已加载来源的注入去重键，视频区间可能形成 `reference#start-end` |

参数错误或视觉能力不支持时也可能返回 `error`。部分成功时应同时检查 `loaded` 和 `skipped`，不能只检查 `ok`。

处理顺序：

1. 工具在线程中加载来源，结果文本记录到历史 JSONL；单个来源读取失败不影响其他有效来源。
2. 已加载部件在内存中复用并追加到后续模型请求，通常不重复读盘或转换；审批恢复后的缓存结果按需重新加载。Chat Completions 可包含 `image_url` / `video_url` / `input_audio`；Messages/Responses 没有原生音视频块——视频转关键帧拼图（单图，见 §4），音频给精确到类型的拒收说明（文件名+接口名，不再音视频混写）。
3. 请求发送前，再按整份请求的供应商配额裁剪；被移除的部件变成“未发送”文本占位，并向模型说明当前限制。

本地及会话媒体通常使用 base64；常规网络来源也可能直接发送 URL。base64 不进入工具结果或历史 JSONL。请求裁剪不修改用户原文和历史存档。

首次自动探测到供应商限制时，前一条工具结果可能已经记录“加载成功”，但这并不代表供应商实际接收了全部数据；以随后“未发送”占位及限制提示为准。模型不能声称已经看过未发送内容。

## 4. 重读、转换与大小限制

- 当前上下文中仍保留的图片/音频按注入键去重，重复调用可能返回 `already_injected`。受请求配额移除后允许再次读取。
- 新视频片段注入时旧视频画面被回收，目前单批仅保留一个视频片段；同一视频不同区间可继续读取，已回收区间也可回看。
- 大于 2 MiB 的图片可能降采样，长边上限 1568，JPEG 质量使用 `quality`。小图通常保留原数据。
- BMP、ICO、TIFF、静态 GIF 等按需要转换为支持的图片格式；Chat Completions 下动态 GIF 通常转换为 MP4，**占用 video 配额，不占 image 配额**。Messages 下 GIF 仅发送静态首帧，按图片处理。若特定转换路径回退为首帧图片，则按实际生成的部件类型处理，不代表模型看到了完整动画。
- 读取侧常规静图上限 30 MiB、音频 20 MiB、视频及动态 GIF 600 MiB；用户上传入库的图片上限为 20 MiB。文件大小限制与 `mediaLimits` 的数量限制是两回事。
- 视频读取/转换依赖 ffmpeg，优先使用系统 PATH，再使用 `imageio-ffmpeg`；转换失败或格式不支持时查看工具返回原因。
- 视频关键帧拼图（2026-10-28，Messages/Responses 有视觉模型）：该协议无原生视频块，用户附件与 read_media 的视频统一转为 6 帧时间戳网格拼图（单图，随附区间/截断说明），无音频内容；无视觉模型仍只留引用占位。这与配额禁令是两回事——`mediaLimits` 禁止视频时工具层直接拒绝，绝不会转拼图绕过（见下段）。

逐个读取多个媒体时，应先记录已读取内容，再读取下一份。配额限制可能使旧媒体从后续请求中退出；不会自动把多份媒体合成一张图片，也不会把被禁止的视频悄悄变成静态图来绕过限制（上一段的拼图只发生在配额允许但协议无视频位时，且明确告知模型）。

## 5. 供应商限制怎么配置

完整配置示例、总数量与分类数量的关系、继承覆盖规则，以及自动降级的边界见 [供应商媒体类型与数量限制](media_limits.md)。

最常见两种情况：

```json
{"mediaLimits": {"video": 0}}
```

只禁止视频，不额外限制图片数量。省略 `image` 不会开启图片能力，仍需 `vision=true` 和供应商支持。

```json
{"mediaLimits": {"total": 1, "video": 0}}
```

整份请求最多一个媒体，且禁止视频。一张图片加一个音频也会超过总配额。`mediaLimits` 是供应商/模型的共享请求配置，不是本工具的参数：文档由独立的 `read_document` 读取，其解析文本不占用媒体数量，原生文档 `file` 部件占用 `document` 与 `total` 配额。
