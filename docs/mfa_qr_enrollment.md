# 验证器扫码绑定

2026-10-24：登录页的首次绑定和账号页的可选 MFA 均支持扫码，适配 Google Authenticator、Microsoft Authenticator。

## 操作

1. 在 [本机登录页](http://127.0.0.1:48621/ui/login.html) 输入项目账号密码。
2. 首次绑定时再次确认当前密码，点击 **生成验证二维码**。
3. 手机选择任意一种验证器：Google Authenticator 的 **＋ → 扫描二维码**；Microsoft Authenticator 的 **＋ → 其他帐户（Google、Facebook 等）→ 扫描二维码**。
4. 扫描网页二维码，使用新增 Ytools 条目的 **6 位动态码**，在网页点击 **确认验证码**。扫码后还需提交动态码才算完成绑定。
5. 保存恢复码，按提示完成初始密码修改。以后登录直接输入验证器中的当前动态码，无需重新扫码。

二维码在浏览器本机生成，不使用外部二维码接口或 CDN。手机无需访问电脑的 `127.0.0.1`，也无需同一 Wi-Fi。二维码与手动密钥都是私密资料，不应发给别人。

绑定最长 5 分钟，同时受本次登录到期时间限制；页面显示倒计时。到期、绑定成功、离开页面时，二维码和手动密钥从页面移除。重新生成需再次输入密码；新密钥生成后，旧的未完成绑定条目需替换。扫码困难可展开手动密钥备用。

已绑定账号可以进入 **设置 → 账号与安全 → 验证器管理**，添加或更换验证器，不需要删除账号。旧绑定会保留，直到本人确认新验证器。

## 登录页直接添加／更换（2026-10-25）

1. 刷新登录页，输入账号密码；密码通过后进入验证码步骤。
2. 验证码错误可在本次登录的 5 分钟有效期内直接重试，无需重新输入密码。已验证状态由 HttpOnly Cookie 关联，密码不会保存到浏览器本地存储；登录真正过期或被撤销时才需要重输。
3. 如需增加或切换手机验证器，点击 **扫码添加／更换验证器**，选择操作并输入当前动态码或一条未使用恢复码，点击 **验证身份并生成二维码**。这一步复用本次密码验证，不要求再输入密码。
4. 使用 Google Authenticator 或 Microsoft Authenticator 扫描新二维码，填写新条目的 6 位动态码，点击确认。新码输错时二维码保留，可继续重试。
5. 添加会保留现有验证器；更换会在新码确认后停用全部旧验证器，并显示新恢复码，保存后进入工作区。首次/临时密码账号需先完成普通 MFA 登录并修改密码，再管理验证器。

取消或二维码过期不会更改现有绑定。生成二维码后身份已验证，可直接进入工作区或账号与安全重新发起绑定。旧验证器和恢复码都丢失时，仍需服务器管理员恢复；扫码入口不会绕过双重验证。新入口需新版后端支持，页面通过服务能力标记控制展示。

本机已于 2026-10-25 启用并核验，刷新登录页即可使用。原有绑定和账号库版本保持一致，详细验证见 [登录重试与扫码管理记录](archive/login_mfa_retry_2026-10-25.md)。

## 从微软切换到谷歌，或增加另一台设备

1. 打开“验证器管理”，选择 **添加另一验证器（保留现有）**，名称可填 `Google Authenticator`；如果希望切换后停用全部旧验证器，选择 **更换验证器**。
2. 输入当前项目密码，以及当前微软验证器的动态码或一条未使用恢复码，点击生成二维码。刚用过的动态码要等下一组。
3. 在 Google Authenticator 中用 **＋ → 扫描二维码** 添加 Ytools，再把谷歌应用当前的 6 位动态码填回网页，点击 **确认添加/更换验证器**。
4. 添加时两者均可登录；需要停用微软时，在列表里移除“原有验证器”，按页面要求填写密码和当前有效动态码。更换时，确认新设备后全部旧验证器停用，旧恢复码失效，需要保存新恢复码。

每个新增验证器使用独立密钥，可单独移除，最多保留 5 个。没有确认的新二维码不会成为有效登录方式；取消/到期保留原有验证器。最后一个验证器不能直接移除，可通过“更换”完成切换。移除或更换会撤销其他浏览器登录；不删除账号、聊天、附件或模板。

若已无法使用旧验证器，可用未使用的恢复码完成验证；没有任何恢复方式时，仍可按 [账号指南](account_quickstart.md) 使用服务器本机管理命令恢复。

设备丢失时，登录页提供直接用恢复码更换丢失设备的入口；恢复码可下载，已登录账号可重新生成备份。没有任何设备或恢复码时，详见 [设备丢失恢复指南](account_recovery.md)。

## 实现与验证

- 使用标准 `otpauth://totp/` URI，issuer 为 Ytools，SHA-1 / 6 位 / 30 秒，兼容两种验证器的第三方 TOTP 账号。
- `qrcode-generator@2.0.4` 精确锁定，保留 MIT 许可；浏览器加载的副本与 npm 包校验一致。
- 绑定信息仍由受 Cookie、Origin、CSRF、当前密码保护的 POST `/auth/mfa/start` 返回；新增 `expires_at` 仅告知页面截止时间，没有新增公开二维码/密钥接口。
- 共用组件 `H5/js/mfa_enrollment.js` 负责二维码、手动备用、失效清理；登录与账号页面共用，脚本及资源均按内容哈希版本化。
- `security/mfa_devices.py` 负责已绑定账号的独立设备管理；新增配置只在新动态码确认后原子启用，需当前密码和已有 MFA/恢复码双重证明。密钥加密存储，待确认操作绑定当前登录、账号及配置版本，5 分钟到期；设备列表只返回名称/ID，不导出已有密钥。
- 登录专用 POST `/auth/mfa/manage/login_start` 仅接受尚未完成 MFA 的有效短期登录，验证当前 MFA/恢复码后轮换登录凭证，再生成新绑定。不能使用匿名请求、普通长期登录或待修改初始密码的账号代替这一步。账号页原有的密码＋当前验证码校验保持不变。
- 账号库版本 3 增加设备/待确认表；版本 4 再增加服务器恢复后必须重新绑定的标记，保留原有主验证器的密文与计数器。正常升级无需重新绑定，离线 `reset-mfa` 会清理全部验证器并要求重新绑定。
- 独立 ZXing 解码器检查实际生成图片，覆盖普通/最长用户名；解出的 URI 通过独立 HMAC 动态码算法完成真实 HTTP 绑定、退出、再次登录和重放拒绝。测试仅使用临时账号，没有替用户绑定手机。
- 前端测试覆盖两种页面、脚本顺序、离线生成、生成失败备用、超时、浏览器返回清理、重新确认密码及绑定后清理；实际测试汇总见本轮结果。Linux 的独立解码测试在没有 Node.js 时跳过，后端流程仍单独验证。

2026-10-24 已绑定账号管理验证：

- 后端设备管理专项 **11 passed**，覆盖添加、更换、移除、过期/取消、重放、跨账号访问、CSRF/Origin、并发配置失效、数量限制、旧库升级和离线恢复；Windows 开发环境、实际服务 Python 3.14 与 Linux 分别验证。
- 前端账号与二维码专项 **14 passed**，前端全量 **781 passed**；最后调整后重跑专项与资源哈希校验通过。
- Windows 身份、HTTP、资源、独立扫码与资产集成回归 **60 passed**；实际服务解释器回归 **59 passed**；Linux 身份/HTTP/设备管理回归 **43 passed**。这些集成检查之后增加的 CSRF/Origin 和并发设备专项另行验证；测试均使用临时账号。
- 两项独立扫码解码在已安装 ZXing 和 Node.js 的 Windows 测试环境通过；缺少解码工具的环境可跳过这两项，浏览器端不依赖这些测试工具。

首次加载新版后端会自动创建当前版本所需附加表（现为版本 4），不修改现有账号的主验证器绑定。升级前应备份账号库及 `mfa.key`；重启服务应避开正在运行的模型任务。更新代码后刷新账号页，在“验证器管理”中操作。
