# 登录用户名修改

入口：设置 → 账号与安全 → 修改登录用户名。显示名仍单独修改，账号 ID、角色、历史、附件、版本和配额不会随用户名移动。

## 使用规则

- 所有账号均可修改，包括名为 `admin` 的管理员；权限由账号角色决定，不取决于用户名。
- 每次提交都验证当前密码。已启用 MFA 的账号还需有效动态码或一条未使用恢复码；管理员、操作员必须先启用 MFA。
- 刚用于登录的动态码不能再次使用，可等下一组；恢复码使用后会消耗一条，不会重置其他验证器或恢复码。
- 用户名为 2–64 个英文字母、数字或 `_.@+-`，以字母或数字开头。后端沿用 NFKC 和大小写归一化，确保重名判断一致。
- 成功修改后冷却 30 天。旧名永久保留占用，停止登录，其他账号和本人均不能再次选用该旧名；提交前请核对确认框中的新名。
- 成功后撤销全部设备的登录和未完成验证器绑定，使用新用户名、原密码及原验证器重新登录。显示名不自动改变；手机验证器的标签可能仍显示旧用户名，可在验证器内自行改标签，无需重新扫码绑定。
- 已授权的后台任务继续绑定原账号 ID；重新登录后可继续查看。改名不调用账号禁用/降权时的任务停止逻辑。
- 验证失败保留当前登录；密码仅保留在本页输入框供重试，不写 Web Storage，成功或离开页面时清除。

## 安全与存储

账号库 schema 6 新增 `username_history(username, user_id, retired)`，用于旧名保留和账号级冷却。创建账号和改名共用旧名占用检查；改名使用唯一索引及单一 SQLite 写事务，原子完成动态码/恢复码消费、旧名登记、新名更新、认证版本递增、全部登录撤销和审计。

密码校验在写事务外进行，进入事务后重新核实登录、账号角色、密码版本及有效状态。防止改名与登录并发时，旧用户名的密码校验结果创建新会话。失败的重名/冷却请求不消费 MFA 码，不撤销登录。尝试限流按固定账号 ID 记账，换 Cookie 不会重置。

`GET /user/username`：查询本人当前用户名、MFA 要求、下一次可修改时间及是否可操作。

`POST /user/username`：提交 `username`、`password`、可选 `code`。请求接受登录、MFA、初始密码状态、Origin 和 CSRF 检查；不能提交其他账号 ID 或修改角色。成功删除当前 Cookie，并返回 `relogin_required=true`；冲突 409、冷却 429（含 Retry-After）、身份验证失败 403。管理员创建重复或保留名称返回明确的 400。

敏感操作审计只记录固定账号 ID 和修改前后用户名，不记录密码、动态码、恢复码或密钥。

## 恢复与升级

启用前私有备份完整账号 SQLite（含全部表）及 `mfa.key`；历史数据目录无需迁移。完整受管备份自动包含 `username_history`，恢复后仍拒绝旧名注册。本次升级不主动改名、不撤销现有登录、不重置密码或验证器。

忘记当前用户名时，服务器管理员可在项目目录运行 `python scripts/manage_accounts.py list` 查看当前账号列表。重置密码/MFA 等离线维护命令应使用当前用户名。不要为改名或更换验证器删除账号。

实现及验证：`security/usernames.py`、`test/test_username_changes.py`、`H5/test_h5/username_management.test.js` 和真实浏览器 `username_change` 流程。验证只使用临时账号；不登录或更改真实管理员账户。
